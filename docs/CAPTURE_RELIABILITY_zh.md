# 十台重新校准：采集可靠性改进

2026-11-12：接收器入队确认及无线响应时序修复后，十台约80秒试录生成并保存40,159个唯一窗口；随后使用现有固件完成十分钟任务，每台实际采集590–591秒，共295,248窗，均通过零缺口门槛。此前三轮分别缺1、1、2窗的记录保留为失败证据。当前安装版本及剩余验收见[状态表](STATUS_zh.md)；传输通过不代表校准精度已验收。

## 本页的对比对象

下文旧版F04、裸ACK释放和重同步停顿是本项目中间实现的历史记录。当前jitingcn上游本来就有原始采集、单目标ARQ重传、批量采集与TDMA；本项目新增F04积分窗／入队收据／结束审计，并修改已有调度和恢复路径。上游与本项目的文件证据见[采集与调度对照](UPSTREAM_DIFF_zh.md#33-采集重传与普通追踪调度)。本页没有两套完整固件的同条件丢包率基准。

## 选择的方案

保留传感器本身的高频采样，在各台设备内把每个约 20 ms 窗口的全部样本积分，再传输 50 Hz F04 摘要。采用校准专用时隙、接收确认、短时 RAM 排队以及结束清单。无需在每次校准前更换专用固件。

旧版 F04 绕过 TDMA，十台自主发送并在失败时进行硬件重试；普通姿态也在竞争带宽。源码证明这些竞争路径存在，但不能仅凭源码把历史每一个缺口都归因于碰撞。

当前实现在批量采集期间采用每台 32 tick（约 0.977 ms）时隙。十台一帧约 9.77 ms，每台理论约 102 次发送机会/秒，生产率约 50 个窗口/秒。数据包48字节，接收器确认24字节，自动硬件重发次数为零：未收到匹配确认的窗口保留在RAM队首，下一个时隙重试。旧版只凭裸硬件ACK释放窗口，曾出现Tracker计为已提交、接收器转发流却没有该窗口的情况。新版要求接收器验证并成功入队后，返回匹配设备、启动、采集轮次、序号和内容CRC的确认；它仍不代表主机已保存。

Tracker 在收到新的宽时隙配置且时钟同步新鲜后才开始窗口累计。严格入口只在能容纳一次交换的窗口内启动，迟到、失去同步、无线忙或无法排队时均延后。同一时隙最多一次尝试；发送入口共用互斥锁，避免其他线程启动自动排空 FIFO 导致校准包抢跑。常规姿态包在 F04 活动期间暂停，PING 和控制保留，停止后恢复。其余非校准控制流量、时钟估计误差、调度延迟仍需实机验证。

队列为 64 × 48 字节，约 1.28 秒容量。它是短暂故障缓冲，不能抵抗长时间遮挡或断电。STOP 先停生产，最多排空 2 秒，再在 1 秒内尝试发送三份结束清单。清单包含生成序号上界、有效/无效窗口、队列溢出、收到匹配入队确认的窗口数、未排空尾部、延后次数和末尾不足 20 ms 的样本数。重复清单必须一致，缺少清单则尾部完整性未知。

接收器必须在底层ACK等待预算内完成验证：采用等价的CRC32查表，RADIO回调仅校验与入队，USB工作由批量期间的2ms定时器调度。另修复最后一次确认超时后残留等待标志阻塞普通姿态的退出路径。协议和计数含义见[F04协议](../integration/F04_PROTOCOL.md)。

## 为什么暂不保存完整原始流

| 方式 | 每台数据量 | 当前硬件适用性 |
|---|---:|---|
| 48 字节 F04 × 50 Hz | 2.4 KB/s；10 分钟 1.44 MB | 无线可行；内部存储放不下整轮 |
| 假设仅保存 7 个 float × 409.6 Hz，不含时间/序号 | 11.47 KB/s；10 分钟约 6.88 MB | 十台并传需要更大带宽，内部存储更不足 |
| 当前 RAM 队列 | 3,072 字节 | 短时排队及重试 |

板上 nRF52840 内部 Flash 总量 1 MiB；既有分区已分配给两个固件槽、NVS 和启动加载器。OTA 备用槽约 448 KiB，即使全部挪用也仅约 191 秒 F04，且会改变升级与恢复方案。现有 ARC 归档是压缩校准观测，不是完整可重放的同步时间序列。

若实机仍无法稳定采集，下一阶段优先考虑**按动作分段、本地缓存后轮询导出**：每段必须预先限制容量；块包含启动/会话/样本序号、采样时间、CRC；主机 ACK 缺块重读，并在整组下载校验完成后才允许下一段。长时离线采集更适合加外部 Flash，或使用多个接收器分组。专用固件可腾出部分 RAM、减少实时任务，但不会自动提供足够存储或精确同步。当前未实现这些增强，不占用 OTA/NVS 分区。

## 新录制及验收

`tools/batch_record_only.py --session <目录>` 默认有开始屏障：所有冻结身份均收到至少 200 个从零开始的连续唯一窗口，且最后数据不超过 1 秒，才报告 `all_ten_fresh=true` / `ready=true`。45 秒仍未就绪会在动作开始前停止并留下诊断。只有 READY 后才开始移动夹具。

READY 不表示十台采样瞬间相同。F04 仍使用设备内估计采样时间；开始屏障消除“有人还没开始录”的问题，不替代后续时钟对齐。

### Helper读取阻塞修复（2026-11-12）

发现录制准备阶段主HID接口的 `read(64, 0)` 被误当成非阻塞轮询。打包使用的Python hidapi在超时参数为0时实际调用 `hid_read`，而主接口此前没有设置非阻塞；F04开始后普通姿态暂停，等待主接口数据会同时拖住校准HID接口的读取。现场两轮出现主机读取间歇、接收器反压和设备队列溢出，最终严格READY门槛拒绝，两轮STOP均确认。朝向记录为十台+X，不能仅提示用户继续静止。

修复在主HID打开后显式设置非阻塞，带正数超时的身份／命令等待仍使用限时读取；模式设置失败时关闭句柄并释放锁。此修复也覆盖其他使用同一Radio零超时轮询的录制入口。READY失败现在逐台说明数据不足／缺口／过期、朝向不符或仍在转动，并给出诊断路径；不降低完整性门槛、不延长等待来掩盖缺口。回归覆盖普通姿态完全静默时的校准录制与停止。

随后实机对照发现第二个问题：修复后保持SlimeVR开启的一轮仍因接收器反压和设备队列溢出失败；仅退出SlimeVR及其服务器后，下一轮通过READY，观测时十台已保存24,893个窗口，首部和内部缺口均为0。当时尚在录制，不能当作整轮尾部验收。该对照支持当前组合存在并行运行冲突，具体是SlimeVR访问方式还是接收器USB调度仍未定位，不能泛化到所有SlimeVR版本。

这轮随后完成了X轴正反转：十台共122,312个唯一窗口，结束清单及STOP确认通过，首部／内部／尾部缺口、无效窗、队列溢出和尾部丢弃均为0；自动分段接受为有效X轴录制。用户随后进入Y轴。这补充了整轮传输及X轴动作分段验证，尚不等于四次录制全部完成或校准精度验收。

当前校准录制应先退出SlimeVR，包括后台服务器。Windows下Helper在启动录制前检查SlimeVR进程或其自带Java服务器，若发现则说明原因并阻止本轮开始，不自动终止其他程序，也不清除已有有效录制／计划。该检查依赖标准进程名或Java可执行文件位于SlimeVR目录；自定义启动器、系统Java启动的后台服务器或其他平台仍需操作者确认已退出。普通追踪时可照常运行SlimeVR。

开始动作后不逐姿态提问，也不因缺口自动中断。仍在 `active-recording.json` 指定位置创建 `STOP_RECORDING` 结束。`--passive` 可用于旧固件或纯诊断，不通过就绪门槛也继续录制；结束质量门槛仍保留。

原始报告以及接收器停止结果保存在 `reports.jsonl`，`quality.json` 给出逐台完整性。新校准默认要求：

- 全部目标均有唯一启动/采集身份，CRC、物理范围和时间顺序有效；
- 每台至少 200 个窗口，首部、中间、尾部缺失均为零；
- 每台均有一致的结束清单，无设备无效窗口、队列溢出和未排空尾部；
- 接收器 STOP 已确认，USB 转发 dropped 为零；
- 乱序在有限重排范围内可恢复，重复去重，冲突重复或无法恢复的迟到包失败。

这是保守的**传输门槛**，并非校准精度门槛。总缺失率再低也可能恰好丢掉一个动作，因此本轮重校准先按零缺口验收。停止时不完整的最后一个窗口单独计样本数，不冒充完整窗口；动作须在 STOP 前完成并放稳。

`tools/jointcal/prepare.py` 会从原报告重新计算完整性，默认拒绝不通过的数据。`--allow-legacy-transport` 仅允许继续做旧数据诊断，会在输入和报告中标记覆盖，不能据此宣称数据完整或安装许可。

## 联合求解仍需改进和验证的方面

1. **采样时间**：目前是 FIFO 首次处理时刻加采样周期，仍非硬件时间戳。下一步应同时记录传感器计数/时间、设备 RTC 和同步锚点；不能把无线到达时刻直接当采样时刻。TDMA 和重试也不会提高时间戳精度。
2. **刚体位置差异**：继续使用共享角速度、每台独立安装方向及力臂的模型，包含 `α×r + ω×(ω×r)`；不能把十台加速度强制相同。
3. **20 ms 压缩误差**：F04 保留角增量和加速度均值，不能恢复窗口内完整波形、锥运动交叉项和高频相关性。适合目前缓慢、近单轴的动作；更快或多轴运动应增加子窗口/预积分信息并作对照。
4. **Earth 与温补分离**：动作时冻结温补写入，记录每台实际温度；采集前确认温表覆盖。增加同姿态的独立升降温验证，避免时间漂移、温度和地球项互相吸收。原 Earth 每台 RMS ≤0.001°/s、g-sens ≤0.006°/s 门槛不放宽。
5. **独立验证**：三轴比例的拟合内 20 圈数据不能兼作提升精度证据。重采应另留不参与拟合的旋转/静置段；运动留出和温度循环验证通过后，才评估写入候选参数。

## 连接 SlimeVR 时的普通姿态链路

当前安装使用 Tracker → ESB 无线 → Receiver → USB HID → SlimeVR。普通姿态发送的是设备内融合后的四元数，不需要 SlimeVR 收齐每个原始陀螺样本再积分。采集期间暂停这条姿态流，停止后恢复。

普通姿态构建启用 TDMA、关闭 `CONFIG_CONNECTION_ENABLE_ACK`。普通包不等待无线 ACK，也不逐包补传；干扰、发送队列拥塞或接收缓冲不足均可能表现为缺帧。接收器按每台的 8 位序号识别相同序号和短距离倒序，并丢弃这些包，避免通常的重复／迟到包覆盖较新的姿态。这个序号没有启动身份：倒退小于64判为旧包，前跳大于80按重启处理，不能严格区分长时间断流、序号回绕和设备重启；因此丢包率只是序号缺口估计，并非端到端精确统计。

接收器的普通 HID 队列按顺序发送，USB 提交失败会保留队首重试；队列满会丢弃新报告并累计 `hid_drop_total`。传给 SlimeVR 的标准16字节记录不包含无线序号，无法仅靠 SlimeVR 收到的包反推出精确丢失数量。静止时固件也会降低姿态更新率，所以报告间隔变长不能直接等同于空口丢包。

少量缺帧通常表现为短暂停顿或延迟，后续姿态包可继续更新；它本身不会重置设备内部融合方向。持续的肢体扭转还需要结合设备重启、融合／校准状态以及服务端重置记录判断，不能只凭掉帧推断原因。普通实时流适合限制延迟并优先采用新姿态；F04校准则必须保留每个积分窗口，两者采用不同的确认策略。F04接收器入队确认修复不意味着普通姿态流也已获得逐包完整性保证。

2026-11-12现有固件的普通链路实测：约4分钟的首末详细统计快照之间，十台接受29,344包、序号缺口341，合计估计1.15%，逐台0.88%–1.52%；无新增重复、倒序或重启判定。计数包含普通状态／信息包，序号在发送入队前分配，因此不能区分发送端跳过、空口丢失或接收端拒绝，更不等于纯姿态包丢包率。240秒全精度姿态共2,325份，最大相邻变化0.01524°；4号一次3.047秒全精度报告间隔前后变化0.00428°，未见明显突跳。当前构建的`health`返回需启用`CONFIG_TDMA_DIAGNOSTICS`，故普通HID丢弃计数不可读，不能记为零。上述观察不证明动态佩戴时不会卡顿。

仍可读取普通周期日志：开启统计后首条报告累计27次HID丢弃。源码只在详细统计开启时清零该周期计数，因此首条包含开启前的累计值，不能全部归因于本次观测；其后无新增丢弃日志。周期日志不能替代首末累计计数快照或端到端确认。

实机顺序：核对备份与固件身份 → 使用匹配固件完成十台静置试录 → 短暂干扰/遮挡恢复试录 → 检查每台完整性 → 再进行完整校准动作。已有匹配固件时无需为每次试录重复刷写。本轮静置短录制已通过，遮挡恢复和正式重校准尚未进行。

此次修正能够由代码确认的恢复缺陷：

1. F04 在时钟同步超过约 2 秒时停发，原心跳仍使用普通连接递增退避，同步完全失效（age=-1）也不触发提前重同步。显式采集期间改为健康同步每 600–750 ms 更新；失同步或同步年龄达到 1 秒后，每 160–310 ms 重试。间隔随设备和尝试次数改变，避免固定相位重复碰撞。普通追踪的省电退避不变。
2. 共享射频管道内其他设备或旧计数器的 PONG 不再清除本设备失败或执行命令，仅接受当前探测的设备与序号。采集等时隙移到 TX 锁外，获得锁后重查时隙。
3. 接收器将成功校验且入队的 F04 作为成员存活证据，避免采集暂停普通姿态时，仅因心跳未到而剔除仍在传数据的设备。RADIO 回调只刷新原子证据，不唤醒任务；原监控线程负责合并。
4. Helper 持续显示超过 1 秒没有数据的设备和停顿时长，继续录制，结束时严格审计。不以扩大缓冲、插值填缺或放宽零丢失门槛掩盖问题。
